## Destination

A **build-ready blueprint** for the autonomous FPL gaffer on the Pi 4B (2GB): every architectural decision locked (agent runtime, LLM endpoint, Telegram flow, approval flow, actuator approach, repo layout, stage order) and a spec + staged roadmap another session can execute without further decisions.

## Notes

- System shape: Python math pipeline (collector → projections → ILP optimizer) + LLM "gaffer" via Telegram; cron wakes 1–3x/day + wake-on-message; approval mode — no FPL write without explicit Telegram "yes".
- LLM brain remote (OpenAI-compatible endpoint); all context/memory on the Pi as files; secrets (bot token, API key, FPL cookie) Pi-only.
- Standing decisions from charting: **pragmatism-first** runtime choice; **~$5/mo** API ceiling (lean prompt assembly is a design constraint); **this repo = source of truth, Pi pulls**; actuator **in scope, feasibility-gated**; **GW1 pre-deadline run in scope as task work** (deadline Fri 2026-08-21 17:30 UTC).
- Security standing rules (from claw research): memory-poisoning of persona/memory MD files is demonstrated; SKILL.md = executable code; allowlist own Telegram user ID; keys outside agent-readable workspace; no exposed ports (long-polling only).
- Facts: Pi host `fplpi`, user `saf`; FPL entry id in gitignored `.env` (`FPL_ENTRY_ID`, see `../.env.example`); prior-effort spec at [fpl-agent-system.md](../fpl-agent-system.md).
- Skills per ticket type: /grilling for grilling tickets, /research for research, /prototype when the visualizer graduates.

- **Runtime locked: minimal DIY Python daemon** ([#7](https://github.com/ropats16/fpl-pi-manager/issues/7) grilling, 2026-08-18) — chose a ~500-line custom Python daemon over adopting a claw framework; **Hermes dropped** (OOM risk on 1.8 GiB usable, heaviest Py+Node+ffmpeg stack, refuses <64k-ctx models — buys nothing a single-user cron+long-poll agent uses); PicoClaw/ZeroClaw **not adopted but their conventions borrowed** (both were *active* as of the research — Pico v0.3.1 3 Jul, Zero v0.8.4 2 Aug — the "outdated" instinct was the coding-agent hype cycle, not death). **Rationale (priority order):** (1) whole repo is already Python with an offline-selftest idiom; (2) the daemon workload is genuinely ~500 lines and mostly *custom* domain logic (multi-agent gaffer, Scout, chip engine, learning loop), not stock claw behavior — the claw ecosystem optimizes for a personal-assistant-that-remembers, which this isn't; (3) testability is strictly better when you own the HTTP edges; (4) smallest attack surface — no untrusted-skill plugin system to defend (sidesteps the demonstrated SOUL/MEMORY.md poisoning + "SKILL.md → shell in 3 lines" risks, which are framework-shape risks not data risks). **Runtime-skeleton conventions locked here (only):** context **assembled from markdown at runtime** (nothing hardcoded — serves the ~$5/mo lean-prompt ceiling *and* testability); **state = JSON** (`season-state.json`, write-back invariant) / **narrative memory = Karpathy LLM-wiki markdown** (repo's existing house style); a **jobs config** (cron-shaped) with **explicit `deliver` semantics** so a wake that should message can't fail silently (PicoClaw's documented footgun); avoid the `AGENTS.md` filename collision (repo README vs claw rules file). **Activity shape** (entailed by "daemon", reaffirmed from charting): resident process = always-on Telegram long-poll (wake-on-message) **+ cron scheduled wakes 1–3×/day**, `systemd Restart=always`. **HTTP-edge testability — confirmed holds** (acceptance criterion): three mockable seams — **LLM** (OpenAI-compatible base_url), **Telegram** (long-poll), **FPL write/actuator** (fake-by-default until feasibility-proven); an offline **`daemon selftest`** drives the whole wake→brief→approve→act loop with zero network, mirroring `run_pipeline.sh offline`; the approval gate (no FPL write without explicit Telegram "yes") lives in the glue *above* the actuator seam. DIY makes this hold *better* than any framework (a compiled binary seals these edges). **Trial-vs-commit: commit-now** (no framework spike). **Exit strategy:** abandoning DIY costs ~rewrite of the 500-line glue; everything valuable — persona/memory markdown, the file *set*, the whole math pipeline, decision-log format, prompts — is **portable files, zero lock-in**; keeps PicoClaw as a cheap escape hatch, inverting the research's "trial-first" path. **Deferred, not decided here:** LLM endpoint/model ([#8](https://github.com/ropats16/fpl-pi-manager/issues/8) — Kimi K2.5 / qwen-plus / **GPT-5.4/5.5 candidates to A/B via OpenRouter**); persona/workspace/memory file *set* + single-vs-multi + prompt-assembly size bound ([#9](https://github.com/ropats16/fpl-pi-manager/issues/9)); security *mechanisms* ([#10](https://github.com/ropats16/fpl-pi-manager/issues/10)); exact schedule/supervision/Pi-pull cadence ([#11](https://github.com/ropats16/fpl-pi-manager/issues/11)); build deps + first live loop ([#15](https://github.com/ropats16/fpl-pi-manager/issues/15)). Unblocks #9/#10 (and #11/#15 once their other blockers clear).
